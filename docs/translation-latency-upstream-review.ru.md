## Отдельная ветка LiveKit Agents

Проверена [feat/livekit-agents-rewrite](https://github.com/google-gemini/gemini-live-translate-livekit/tree/5adb161c9237d77b17b2d54c7e0a323c5303daa5), вершина `5adb161` от 28 мая 2026 года. Ветка не является частью upstream main; соответствующего PR в полученном списке открытых/закрытых PR не обнаружено.

Это значительная переработка: Python LiveKit Agents, маршрутизация нескольких говорящих, другая организация комнат и субтитров. В конфигурации указан gemini-3.1-flash-lite-live-translate и streamingTranslationConfig; в нашем сервере — gemini-3.5-live-translate-preview и translationConfig. Код подключения нельзя переносить без проверки протокола и модели.

Полезные идеи:

- Идемпотентное завершение, отмена задач, явное освобождение AudioStream и AudioSource.
- Переподключение с увеличением интервала попыток и случайным разбросом; ожидание можно прервать при закрытии сессии.
- Пересчёт необходимых переводов по событиям комнаты с объединением частых событий; короткий период сохранения ненужной сессии для защиты от частых переключений. В нашем менеджере уже есть пересчёт и период ожидания, поэтому сначала сравнить поведение, а не дублировать механизм.
- Явный маркер окончания высказывания в протоколе субтитров. У нас уже есть segmentId/final; полезно проверить обработку завершения без дополнительного текста.

Ограничения найденной реализации:

- Определённая bounded queue ограничивается количеством элементов, а не длительностью аудио; в просмотренном session.py она не используется для публикации.
- Обработчик входящих сообщений Gemini ожидает публикацию аудио в AudioSource. Это не готовое решение независимой доставки текста и звука при медленном воспроизведении.
- Группировка субтитров по высказываниям не обеспечивает их синхронизацию с реально воспроизводимым звуком.
- Переподключение и отмену параллельных задач всё равно нужно проверять на гонки. Наличие этих конструкций не подтверждает корректность всех сценариев.

Решение: использовать отдельные идеи в существующей архитектуре TypeScript/NestJS. Миграция на Python Agents в ТЗ управления задержкой не входит.

## Что учесть при реализации ТЗ

1. До усложнения очередей покрыть тестами конкурентное завершение мостов, очистку callback и освобождение reader/AudioSource.
2. Восстановление реализовать с отменяемым ожиданием, увеличением интервала попыток, случайным разбросом и защитой от запоздалых событий старого соединения.
3. Проверить явную финализацию текстового сегмента без нового текста, сохранив существующую поддержку промежуточных обновлений.
4. Сохранить нашу архитектуру, текущую модель и контроль очередей. Готового upstream-решения полного ТЗ не найдено.

Код upstream при этой подготовке не переносился. Для продолжения использовать [ТЗ на реализацию](translation-latency-implementation.ru.md).
